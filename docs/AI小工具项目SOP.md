# AI 辅助小工具项目：标准操作流程 (SOP)

> 适用场景：用 AI 做完任何小工具/脚本/自动化程序后，把它**固化、存档、可复现**。
> 核心原则：**让 AI 全程替你执行，你只需要审批和测试。**

---

## 一、项目阶段总览

```
需求确认 → 开发 → 测试 → 打包固化 → 上传 GitHub → 设置开机运行（如需）
```

---

## 二、每个阶段的具体动作

### 阶段 0：需求确认（给 AI 下达指令前做）
在告诉 AI 要做什么之前，你需要想清楚这 3 件事：

| 问题 | 例子 |
|------|------|
| 它要干什么？ | 鼠标侧键改为复制/粘贴/语音 |
| 边界在哪里？ | 只影响我自己的电脑，全局生效 |
| 成功的标准是什么？ | 浏览器不再后退，语音能唤醒 |

> **银月建议**：哪怕三句话说清楚这 3 点，AI 做出来的东西偏差就会小 80%。

---

### 阶段 1：开发（AI 全程替你做）

给 AI 的指令模板：
```
帮我做一个 [功能描述]。
要求：[核心规则 1]、[核心规则 2]
成功标准：[测试通过的判断条件]
所有代码和配置，你直接在后台完成，不要教我怎么做。
```

AI 应该自动完成的事：
- [ ] 写代码
- [ ] 处理依赖（安装库/工具）
- [ ] 处理权限问题
- [ ] 在后台运行/测试

---

### 阶段 2：测试（你来做，AI 辅助分析）

测试清单（每次做完小工具都过一遍）：

- [ ] **核心功能正常**：逐一验证每个功能点
- [ ] **边缘情况**：极端操作（比如双击太快/太慢、空白输入框等）
- [ ] **冲突检测**：和其他已有软件有没有打架
- [ ] **重启后是否依然生效**（开机自启类工具必测）

如果发现问题，直接截图/描述症状扔给 AI，**不要自己动代码**。

---

### 阶段 3：打包固化（AI 执行，标准文件结构）

每个项目的文件夹，让 AI 按以下结构创建：

```
项目名/
├── scripts/          # 核心脚本
├── docs/
│   ├── README.md          （必须有）
│   └── troubleshooting.md （排错指南）
├── logs/             # 运行日志（本地，不上传）
├── setup.ps1         # 一键安装
├── uninstall.ps1     # 一键卸载/还原
├── .gitignore        # 排除 logs/ 等本地文件
└── README.md         # 项目说明（中文）
```

给 AI 的指令：
```
帮我把这个项目打包成标准 GitHub 文件夹结构，
包含：README（中文）、一键安装脚本、一键卸载脚本、排错指南、.gitignore。
在本地初始化 git 仓库并完成第一次 commit。
```

---

### 阶段 4：上传 GitHub（一次性配置，之后 AI 替你做）

#### 首次配置（只做一次）：

1. 注册 GitHub 账号：https://github.com
2. 安装 Git（AI 可以帮你装：`winget install Git.Git`）
3. 配置身份（在终端执行，AI 帮你填）：
   ```bash
   git config --global user.name "你的名字"
   git config --global user.email "你的邮箱"
   ```
4. 创建 GitHub Token（用于 AI 代你推送）：
   - 登录 GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic)
   - 勾选 `repo` 权限 → 生成 → 复制保存

#### 每次上传新项目时，给 AI 的指令：
```
帮我在 GitHub 上创建一个新仓库叫 [项目名]，
把 [本地路径] 这个文件夹推送上去，设为公开/私有。
我的 GitHub 用户名是 [xxx]，Token 是 [xxx]。
```

AI 会执行：
```bash
git remote add origin https://[token]@github.com/[用户名]/[仓库名].git
git branch -M main
git push -u origin main
```

---

### 阶段 5：维护（长期运行的工具）

#### 日志系统（AI 可以帮你加进脚本里）

对于长期运行的脚本，要求 AI 加入自动日志：
- **启动日志**：记录时间、版本号
- **错误日志**：任何 catch 到的异常，写入 `logs/error.log`
- **操作日志**（可选）：关键动作的记录

#### 版本更新流程
每次改动，给 AI 的指令：
```
帮我更新 [功能描述]，
改完后更新 README 的版本号，
打一个新的 git commit（描述：[改了什么]），
推送到 GitHub。
```

## 三、给 AI 下指令的黄金模板

### 开始新项目
```
我要做一个 [工具名]，功能是 [描述]。
规则：[规则1]、[规则2]
成功标准：[怎么算做好了]
全程你来执行，不要教我，直接做。
做完打包成标准 GitHub 结构，本地 git init。
```

### 报错修复
```
[截图/错误信息]
这是 [工具名] 出现的错误，
帮我排查原因并修复，改完直接重启测试。
```

### 功能迭代
```
[工具名] 需要新增 [功能]，
改完后更新 README，commit 并推送 GitHub。
```

### 推送 GitHub
```
帮我把桌面的 [文件夹名] 推送到我的 GitHub，
仓库名 [xxx]，用户名 [xxx]，Token [xxx]，设为[公开/私有]。
```

## 四、专业程序员是怎么做的（你需要知道的最小集）

| 专业实践 | 你的简化版本 |
|----------|-------------|
| 版本控制 (Git) | 每次改动后让 AI 做 `git commit` |
| 错误日志 | 让 AI 在脚本里加 `写入 logs/error.log` |
| 文档化 | 让 AI 写 README + troubleshooting.md |
| 环境隔离 | 让 AI 写 `setup.ps1` / `uninstall.ps1` |
| 代码审查 | 你自己测试，不通过就截图扔给 AI |
| 持续集成 | 暂时不需要，等项目大了再说 |

> **核心心法**：你不需要懂怎么写代码，但你需要懂**怎么描述问题**和**怎么判断结果**。这两件事 AI 替代不了你。
